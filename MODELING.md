# Modelling guide

How a Syuzhet Loom model is written. The model is plain typed data in `src/model/`; the viewer only renders it. The bundled model is an invented example (booking a meeting room); replace `src/model/machines/`, `questions.ts`, `scenarios.ts` and `meta.ts` with your own.

## Files

| File | Contents |
|---|---|
| `src/model/types.ts` | The schema: machines, states, transitions, entry and exit mappings, open marks |
| `src/model/dsl.ts` | Small helpers: `machine`, `s`, `t`, `signal`, `initial`, `final` |
| `src/model/index.ts` | The list of machines and the id of the root machine (`overview`) |
| `src/model/meta.ts` | What the viewer says about the model: title, description, source versions, which ids changed |
| `src/model/machines/*.ts` | The machines. Example: `overview.ts` (overview map, boundary), `booking.ts` (J01, room search, booking hold), `manage.ts` (J02, on the day, check-in, the booking record) |
| `src/model/questions.ts` | Open questions, discrepancies, ambiguities; criteria deliberately not drawn |
| `src/model/scenarios.ts` | Worked scenarios that can be played on the map |
| `src/model/generated/sources.json` | Generated by `npm run extract-sources`: the wording behind every id |

## Rules

1. **States are conditions, transitions are events.** "Room held" is a state; "Confirm" is a transition.
2. **Short labels.** State labels of three words or fewer where possible; event labels likewise. Everything else goes in `description`, `rules`, `guard`, `effects`.
3. **Guards and effects** are written only where they change behaviour.
4. **Journey flows and record lifecycles are different machines.** A journey (`kind: 'journey'`) is what a person goes through. An entity (`kind: 'entity'`) is how one kind of record changes over time. A shared component (`kind: 'shared'`) is defined once and referenced with `uses`. A boundary (`kind: 'boundary'`) is a journey that is not written yet: a labelled box with no states.
5. **Independent dimensions stay separate.** Use a `parallel: true` machine whose states are regions; a region usually `uses` a small machine. Never enumerate combinations. Regions of a parallel machine interact only through `signal(...)`.
6. **Concurrency by multiplicity.** Where many instances run at once, set `multiplicity`, for example `'one per booking'`.
7. **Entry and exit mappings.** A non-parallel machine that is used as a composite defines `entries.default`. Named entries and exits map to state ids. A transition into a composite may name `toEntry`; a transition out of one names `fromExit`, or omits it to mean "from any inner state" (giving up, cancelling). This is what keeps a connection's meaning the same whether the composite is expanded or collapsed.
8. **References.** Every state and transition carries the ids it comes from in `refs`. Ids are never invented; see "Ids" below.
9. **Never resolve a gap.** Where the specification is undecided, draw the documented alternatives and put an `open: { questions, note }` mark on each. An open question is an annotation, not a runtime state.
10. **Mark interpretations.** Where the model adds structure the specification does not state, set `interpretation` on the element (or `interpretations` on the machine) and say what was assumed.
11. **Preserve distinctions.** An empty result is not a failure; an unknown outcome is not a failed one; "asked for" is not "done". If the sources keep two things apart, so does the model.

## Reading aids on every event

Two fields are required on every transition (and `flow` on every signal) outside the overview map. They are the modeller's reading, added so the map is easier to follow; they are not product decisions.

- `actor`: who or what causes the event. `'user'` (the person does it), `'app'` (an automatic outcome or step), `'time'` (a period passing), or `'unstated'` when the sources do not say. Use `'unstated'` honestly: it marks a gap worth closing.
- `flow`: `'main'` for the ordinary flow when things go as intended, including the normal choices a person makes; `'side'` for everything else (failure, retry, cancelling, going back, undo, expiry, recovery, late results, corrections after the fact, less common alternatives). A machine with end states or exits must have a chain of main events from its start to one of them; record lifecycles are exempt.

## Ids

The model cites the source documents by stable id. The families below are the convention the validator, the viewer's search and the trace all share (`scripts/validate.ts`, `src/trace/refs.ts`):

| Family | Form | Meaning |
|---|---|---|
| Decision | `D-12` | A recorded decision |
| Acceptance criterion | `AC-J01-08` | Criterion 8 of journey J01 |
| Open question | `Q-01`, `C-1` | Undecided, or a contradiction between sources. Defined in `questions.ts` |
| Policy parameter | `PN-01` | A number a decision refers to |
| Release priority | `RP-01` | |
| Architecture / evaluation follow-up | `AF-01`, `EV-01` | Something the decisions require of what is built |
| Deferred / superseded / principle | `DF-01`, `S-01`, `P-01` | |
| The model's own label | `MODEL-WORD` | For something worth naming that no source id covers. Use sparingly |

`npm run validate` rejects a malformed id, and warns about an id that is neither in the extracted sources nor an open question.

### Source documents

`npm run extract-sources` reads Markdown tables from the source folder (`workspace/spec/` in the example; see `loom.config.ts`). The first cell of a row is the id.

| File | Row |
|---|---|
| `DECISION_REGISTER.md` (required) | `\| D-nn \| decision \| why \|`, and `\| DF-nn \| text \| note \|`, `\| S-nn \| text \| note \|` |
| `journeys/Jnn-<name>.md` | a heading `# Jnn Title`, and `\| AC-Jnn-nn \| criterion \| from \| note \|` |
| `POLICY_PARAMETERS.md` | `\| PN-nn \| parameter \| … \|` (further cells become the note) |
| `RELEASE_PRIORITIES.md` | `\| RP-nn \| priority \| … \|` |
| `ARCHITECTURE_FOLLOW_UPS.md` | `\| AF-nn \| follow-up \| … \|`, `\| EV-nn \| … \|` |
| any other `*.md` in the folder | hashed for the record, not parsed |

A criterion whose note contains "Merged into" or whose text starts "Withdrawn for now" keeps its id and is reported as such by `npm run coverage`.

## Machine registry (example model)

Ids, and the entries and exits other machines rely on. Renaming one changes every reference to it, including trace references.

| Machine id | Kind | File | Entries | Exits |
|---|---|---|---|---|
| `overview` | overview, parallel | overview | — | — |
| `j06` | boundary | overview | — | — |
| `j01` | journey | booking | default | — |
| `room-search` | shared | booking | default, results | chosen |
| `booking-hold` | shared | booking | default | booked, lost, expired, released |
| `j02` | journey | manage | default | — |
| `meeting-day` | shared, parallel | manage | — | — |
| `check-in` | shared | manage | default | present, absent |
| `booking` | entity | manage | default | — |

Transition ids are derived as `from__to` (then `from__to_2`, …) unless one is given. Give an explicit `id` when two transitions join the same pair of states and you want their ids to say which is which, as `booking-hold` does for `confirming__held` and `confirming__held-unknown`.

## Checking

```
npm run validate    # unique ids, references, endpoints, hierarchy, entry and exit mappings, scenarios
npm run coverage    # acceptance criteria mapped to model elements, non-visual rules, or gaps
npx tsx scripts/list-interpretations.ts   # every interpretation marked in the model
```

Passing validation shows the model is well formed. It does not show the model is right.
